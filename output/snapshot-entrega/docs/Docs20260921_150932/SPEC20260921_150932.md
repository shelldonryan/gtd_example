## 1. Resumo do Produto

### Problema, público-alvo e pitch

A preparação integrada para entrega é uma revisão técnica conjunta do código do jogo Last Horizon. Ela reduz custo de execução e ruído de manutenção por meio da revisão de performance, remoção segura de código comprovadamente não utilizado, consolidação de duplicações, remoção de comentários em arquivos executáveis e reorganização estrutural do sketch.

A feature entra no sketch Processing existente em `last_horizon/` e preserva a experiência observável do jogo. Quests, ciclo de dez dias, recursos, incidentes, riscos, modais, HUD, mapa, movimento, áudio, assets e processamento noturno continuam com os contratos atuais. A conclusão depende da combinação entre regressão funcional, comparação de métricas antes e depois e registro explícito das limitações do ambiente.

A revisão também mantém a integridade do harness e dos scripts de validação. A otimização só é considerada concluída quando existir redução de custo mensurável e reproduzível; sem medição confiável ou sem redução, o resultado permanece inconcluso.

O produto atende três públicos:

- Pessoa mantenedora do sketch: precisa reduzir custo mensurável, diminuir ruído de manutenção e obter evidência verificável de prontidão.
- Desenvolvedor do runtime: precisa reorganizar abas e consolidar helpers sem quebrar compilação, interfaces globais, transições, quests, noite ou interface.
- Jogador do Last Horizon: precisa continuar usando controles, salas, quests, recursos, incidentes, modais, mapa e desfechos com o mesmo resultado observável.

### Stack escolhida

- Runtime principal: Processing 4.5.6.
- Organização do runtime: sketch dividido em abas `.pde`, compiladas como uma unidade e compartilhando estado global.
- Renderização: `PGraphics`, buffer lógico 640x360, saída 1280x720, ampliação inteira, letterbox proporcional, fonte Segoe UI e pixel art sem interpolação.
- Apoio de validação: Node.js em módulos ES, comandos do `package.json` e scripts Bash.
- Arquitetura: funções, constantes, tabelas globais e classes de dados pontuais já adotadas pelo projeto.
- Exclusões arquiteturais: não introduzir engine, dependência, framework de UI, framework web, banco de dados, backend, autenticação ou linguagem externa para quests.

### Plataforma

Aplicação desktop/local e offline executada como sketch Processing. Os comandos Node.js e Bash são ferramentas locais de desenvolvimento, validação, métricas e preparação da entrega. Não existe aplicação web, cliente mobile, API remota ou serviço persistente.

#### Contrato de manifesto sidecar

O modo `--metrics` fixa internamente o cenário inicial de comparação, incluindo sala, estado, conjunto de assets e sequência interativa. O operador não informa esses valores livremente. Cada execução gera automaticamente os metadados do ambiente, da máquina, do hardware, da GPU, do sistema operacional e da versão do Processing; baseline e versão revisada devem usar a mesma fixture e o mesmo perfil de execução.

Cada captura de `--metrics` deve produzir um manifesto sidecar com exatamente os campos obrigatórios abaixo. A representação concreta de cada valor deve seguir o contrato vigente do harness; o comparador deve validar presença e igualdade estrutural entre baseline e versão revisada, sem preencher valor padrão para esconder divergência.

```json
{
  "environment": "<identificador do ambiente>",
  "machine": "<identificador da máquina>",
  "assets": "<identificação do conjunto de assets>",
  "room": "<identificação da sala>",
  "state": "<identificação do estado inicial>",
  "nominal_window_s": 30,
  "processing": "4.5.6",
  "hardware": "<CPU e memória identificáveis>",
  "gpu": "<GPU identificável>",
  "os": "<sistema operacional e versão>"
}
```

`nominal_window_s` deve registrar trinta segundos por referência. A coleta encerra no primeiro quadro cujo relógio atinge ou ultrapassa a janela nominal; por isso, `duration_real_s` pode exceder 30 segundos somente pelo intervalo do quadro terminal. Uma duração fora dessa tolerância torna a amostra inválida. Cada operação de captura, comparação e regressão deve obedecer ao timeout da matriz operacional desta SPEC; timeout excedido encerra o processo, registra diagnóstico e produz `FAIL` quando a operação começou, ou `INCONCLUSIVO` quando o pré-requisito impediu seu início.

`environment`, `machine`, `assets`, `room`, `state`, `processing`, `hardware`, `gpu` e `os` são obrigatórios e devem ser comparáveis; nenhum campo ausente ou divergente permite comparação válida.

`capture.pde` é o produtor canônico do sidecar e do CSV. O sidecar é obrigatório em toda captura de `--metrics`; `compare-metrics.mjs` lê os campos canônicos da SPEC e rejeita amostras que dependam dos nomes legados `duration_s`, `frame_median_ms`, `frame_p95_ms`, `memory_additional_bytes`, `resource_icon_builds` ou `deck_strip_builds` sem uma conversão explícita registrada como parte da execução.

#### Contrato CSV de métricas

O CSV permanece dedicado às métricas numéricas. O contrato lógico deve disponibilizar, por amostra, a duração real decorrida, a quantidade de quadros, a mediana e o p95 do tempo de quadro, o tempo de carregamento, a memória adicional, as construções de ícones, as construções de faixas de piso e as invalidações. Uma forma canônica em snake_case para esses campos é:

| Campo | Tipo | Regra |
|---|---|---|
| `sample_id` | string | Identifica a amostra dentro da referência |
| `duration_real_s` | number | Duração realmente decorrida, separada da janela nominal |
| `frame_count` | integer | Quantidade de quadros coletados |
| `frame_time_median_ms` | number | Mediana do tempo de quadro |
| `frame_time_p95_ms` | number | p95 do tempo de quadro |
| `load_time_ms` | number | Tempo de carregamento |
| `additional_memory_bytes` | integer ou number | Memória adicional introduzida pelos caches |
| `icon_builds` | integer | Construções dos seis ícones estáticos |
| `floor_band_builds` | integer | Construções das faixas de piso |
| `cache_invalidations` | integer | Invalidações seletivas realizadas |
| `allocations_per_frame` | number | Alocações observadas por quadro no cenário interativo |

O registro final pode manter carregamento, memória adicional, construções, invalidações e alocações por quadro por amostra ou em resumo simples; não é necessário criar novos percentis para esses campos. O comparador deve calcular, para cada métrica agregável com p95 e cada cenário medido, a mediana dos três p95 baseline e da versão revisada, além da variação percentual. Para os demais custos, compara a mediana das três amostras. Todos os custos têm menor valor como melhor resultado; uma redução em qualquer custo conta como ganho, desde que os demais custos obrigatórios sejam válidos.

#### Contrato de conclusão

O comparador deve produzir um status geral e um status por custo entre `PASS`, `INCONCLUSIVO` e `FAIL`:

- `FAIL`: qualquer regressão superior a 10% em um custo comparável, falha de carregamento, amostra fora da tolerância de duração, divergência de manifesto ou valor inválido.
- `INCONCLUSIVO`: amostra ausente, ambiente não comparável, timeout antes do início, medição não confiável ou ausência de redução mensurável e reproduzível.
- `PASS`: todos os custos obrigatórios foram medidos, não há regressão superior a 10% e existe redução mensurável e reproduzível em pelo menos um custo alvo.

A precedência do status geral é `FAIL`, depois `INCONCLUSIVO`, depois `PASS`. O comparador deve avaliar tempo de quadro, carregamento, memória adicional, construções de ícones, construções de faixas, invalidações e alocações por quadro sempre que o cenário fornecer a métrica correspondente; nenhuma métrica ausente pode ser tratada como zero ou como aprovação.

#### Workstream obrigatório — otimização robusta em hardware limitado

A otimização deve ser medida antes e depois da revisão em dois perfis: o notebook do usuário, com CPU Core i3 e vídeo integrado, e um perfil de referência identificado no manifesto. Cada perfil executa a mesma fixture, os mesmos assets, a mesma versão do Processing e os mesmos cenários interativos de `--metrics`, com três amostras de trinta segundos por referência. O manifesto registra, para cada perfil, hardware/CPU e memória, GPU, sistema operacional e Processing.

Antes e depois da alteração, o registro deve conter profiling comparável dos hotspots de renderização, escalonamento de imagens, alocações por quadro, preview de transições e carregamento e cache de assets. Cada resultado de profiling deve identificar perfil, versão, cenário, amostra e hotspot, e ser relacionado às métricas do contrato E6 em `code/VERIFICATION.md`.

O gate de entrega otimizada é obrigatório:

- O p95 agregado de tempo de quadro deve ser no máximo 33,3 ms, equivalente a pelo menos 30 FPS, em cada perfil e cenário interativo de `--metrics`. Para evitar que uma média esconda um cenário lento, o p95 agregado da entrega é o maior p95 mediano entre as três amostras de todos os cenários e perfis.
- Nenhum outro custo coberto pelo E6 pode apresentar regressão superior a 10% em qualquer comparação válida.
- `allocations_per_frame` não pode crescer de forma persistente: a mediana final das três amostras não pode exceder a mediana baseline correspondente em nenhum perfil e cenário.
- Não pode haver falha de carregamento. Ausência prevista que use o fallback individual de E2 é tolerada; erro de leitura, formato inválido ou falha não prevista registrada pelo cenário conta como falha.

Se a meta de 33,3 ms, a condição de custos, a condição de alocação ou a condição de carregamento não for atingida, o resultado é `FAIL`. Se o notebook do usuário, o perfil de referência, o profiling ou qualquer amostra obrigatória não puder ser medido, o resultado é `INCONCLUSIVO`. Em ambos os casos a entrega não pode ser declarada pronta ou otimizada.

Os helpers procedurais são unidades reutilizáveis apenas quando mantêm o contrato visual e de interação das chamadas originais. `drawButton` e seu helper de geometria devem registrar a mesma área usada por desenho, cursor, teclado e hit-test. Helpers não podem decidir regras de gameplay que pertencem ao contexto da quest, incidente ou modal.

### 4.3 Camada de API

Não há `fetch`, cliente HTTP, hooks de data fetching ou SSE. O frontend não consome endpoints. A comunicação é feita por chamadas procedurais e estado global do sketch.

| Contrato usado pela interface | Consumidor | Entrada | Retorno/efeito | Estados |
|---|---|---|---|---|
| `uiLayer()` | `screens.pde`, teclado, cursor, mouse e hit-test | Estado atual das telas e modais | Camada ativa única e prioridade de interação | Camada ativa, encoberta ou sem modal |
| `preparePortalTransition()` | `portals.pde`, `movement.pde`, `ship.pde` | Porta e contexto de ida ou volta | Sala destino, saída, chegada, direção e retorno resolvidos uma vez | Preparado, em execução, encerrado e limpo |
| `projectNight()` | painel de sono e confirmação | Estado noturno atual | Projeção baseada em `simulateNightTransition()` | Prévia disponível ou desfecho aplicável |
| `processNight()` | ciclo diário | Estado equivalente ao projetado | Aplicação única da `NightProjection` | Aplicado sem repetição e sem resíduo |
| Cache de ícones e piso | `hud.pde`, `assets.pde`, `ship.pde` | Fonte, escala, largura e geração | Representação estática preparada ou fallback | Válido, invalidado ou ausente |
| Hooks opcionais de captura | harness e scripts de validação | Cenário CLI | Arquivos CSV, sidecar e evidências | Inerte, incluído ou ausente |

O harness não é uma API usada pelo fluxo normal do jogador. Ele deve continuar disponível para `--capture`, `--hit-test`, `--ladder-test`, `--asset-pipeline-test` e `--metrics`, mantendo fixtures de portas, escadas, assets, quests, noite, modais e restauração de tabelas.

### 4.4 Auth Flow no Frontend

Não existe login, registro, logout, sessão, token, JWT, header de autorização ou protected route. A aplicação é local e offline, e o modelo de segurança aprovado não possui autenticação, sessões, roles ou permissões de usuário.

O `test_mode.pde` só é acessível localmente quando incluído explicitamente no sketch de desenvolvimento. Isso não constitui autenticação ou autorização. O módulo não participa do snapshot final, e o destaque visual forçado continua incapaz de autorizar pagamento, aceite, entrega ou conclusão de quest.

### 4.5 Design System

O design system é o sistema visual já existente no sketch. A revisão deve preservar:

- Buffer lógico de 640x360.
- Saída de 1280x720.
- Ampliação inteira e letterbox proporcional.
- O breakpoint crítico é viewport de 640x360: abaixo dele o buffer lógico continua sendo 640x360, sem reflow ou escala fracionária; a saída preserva a escala inteira disponível e aplica letterbox ou corte conforme o espaço físico. Acima dele, a escala continua inteira e a proporção é preservada.
- Fonte Segoe UI.
- Pixel art sem interpolação.
- Paleta existente, textos, números, cores, tamanhos e posições.
- Primitivas procedurais `drawButton`, `drawPanel`, `drawModalFooter`, `drawResourceCard`, `drawMapRoomCard`, `drawTextWrapped` e equivalentes existentes.
- O registro de hit-test comporta no máximo 24 botões por camada; controles além desse limite não são registrados nem interativos, e a tentativa é anotada no diagnóstico sem alterar o layout.
- Sprite principal, orientação, formatos de spritesheet, halos independentes e prioridade de fallback.
- Estados visuais de alerta crítico, transição, chegada, retorno, som e ausência de arte.

O cache de UI é limitado aos seis ícones estáticos de recursos e às faixas de piso preparadas. Números, barras, cores de estado, alertas, piscadas, objetivo e outros dados dinâmicos do HUD não podem ser cacheados. O fallback geométrico existente deve aparecer quando a arte estiver ausente ou parcial.

### 4.6 Estados de UI

#### Estados de renderização e assets

- Asset carregado: prepara os seis ícones quando os assets são carregados ou quando a fonte muda; o desenho normal reutiliza a representação preparada.
- `PImage` estática: é tratada como imutável depois de carregada; uma alteração exige substituir a referência por uma nova imagem, e mutações no mesmo objeto não fazem parte do contrato de invalidação.
- Piso preparado: reutiliza a mesma imagem entre conveses quando tile, largura e geração da fonte são iguais; a imagem compartilhada é tratada como imutável.
- Cache válido: fonte, escala, largura e geração permanecem iguais.
- Cache invalidado: somente caches cuja fonte, escala, largura ou geração mudou são reconstruídos; as invalidações são contadas.
- Arte ausente ou parcial: usa fallback geométrico existente para ícones, piso, sprites, portas, estações e imagens do pipeline.
- Asset inválido ou incompleto: PNG inválido, spritesheet sem os quadros esperados, JSON malformado ou ícone individual ausente usa fallback geométrico somente para o item afetado; a execução continua, e arquivo, tipo de falha e fallback são registrados no diagnóstico da captura.

#### Estados de transição e gameplay

- Transição preparada: sala destino, posição de saída, posição de chegada, direção e porta de retorno já foram resolvidas antes da execução.
- Transição animada: mantém fases de abertura e fechamento e som.
- Transição imediata ou sem arte: continua funcionando sem bloquear a partida.
- Chegada e retorno: preserva posição de saída capturada antes da movimentação, retorno pela posição anterior, gravidade após chegada e travessias entre conveses.
- Quest e ordem: preserva ofertas preventivas, incidentes, soluções, seleção, confirmação presencial, coleta, entrega, retomada e socorro.
- Noite projetada: mostra consumo, perdas de problemas, falhas de quest, riscos, prazos, crises, condições fatais e desfecho quando aplicável.
- Noite aplicada: confirma e aplica exatamente a `NightProjection` já exibida, uma única vez, sem repetir perdas ou consequências; se o estado de origem mudar, a projeção exibida é invalidada antes da confirmação.

#### Estados de camada modal e entrada

`uiLayer()` é a fonte única da prioridade entre pausa, transmissão, incidente, ordens, mapa, diálogo, painel técnico, sono, ajuda e cena. Desenho, registro de geometria, cursor, teclado, mouse e hit-test devem consumir a mesma camada.

- Fechar transmissão revela o incidente.
- `ESC` no detalhe da solução retorna à comparação.
- `ESC` na comparação obrigatória preserva o incidente e pausa.
- Fechar um painel não cancela ordem aceita.
- Estados pendentes são limpos somente nos caminhos correspondentes.
- Nenhum clique ou confirmação alcança controle de camada encoberta.
- `E`, `ENTER`, `ESC`, pausa, mapa, teclado e mouse mantêm os comportamentos validados.

A prioridade e a limpeza de estado são normativas e seguem esta tabela:

| Prioridade | Camada | Fechamento ou `ESC` | Estado que permanece ou é limpo | Próxima camada |
|---:|---|---|---|---|
| 1 | Pausa | fecha a pausa | preserva a camada subjacente e suas pendências | camada subjacente |
| 2 | Transmissão | fecha a transmissão | limpa somente a transmissão; incidente aberto permanece | incidente ou cena |
| 3 | Incidente | sai do detalhe para a comparação; na comparação obrigatória preserva o incidente e abre pausa | não limpa a decisão do incidente até o caminho correspondente | comparação, pausa ou cena |
| 4 | Ordens | fecha o painel | não cancela ordem aceita; limpa somente seleção e paginação do painel | cena |
| 5 | Mapa | fecha o mapa | preserva o estado de gameplay e limpa somente o mapa aberto | cena |
| 6 | Diálogo | fecha o diálogo | limpa diálogo, resultado e alvo do diálogo | cena |
| 7 | Painel técnico | fecha o painel | limpa título e conteúdo técnico, sem alterar quest | cena |
| 8 | Sono | fecha ou confirma a noite | fechamento preserva a projeção; confirmação aplica a projeção válida uma vez | cena ou desfecho |
| 9 | Ajuda | fecha a ajuda | limpa somente a ajuda | cena |
| 10 | Cena | não há modal a fechar | nenhum estado modal é limpo | cena |

Quando flags de várias camadas estiverem verdadeiras, somente a primeira linha aplicável é desenhada e recebe entrada; o fechamento de uma linha nunca limpa pendências pertencentes a outra linha.

#### Rastreabilidade dos critérios das user stories

Cada story tem endpoint HTTP e tabela de banco explicitamente marcados como não aplicáveis porque a arquitetura não os possui. A cobertura real ocorre nos módulos do sketch, nos componentes procedurais, nos contratos de CLI e nas fixtures do harness.

**US-01 — Eliminar trabalho repetido de renderização estática**

- C1: `assets.pde` prepara os seis ícones no carregamento ou mudança da fonte; `hud.pde` reutiliza a representação no desenho normal; métrica `icon_builds` comprova que não há preparação por ícone a cada quadro.
- C2: `assets.pde` e `ship.pde` reutilizam faixas quando fonte, largura e geração são iguais, tratando a imagem compartilhada como imutável.
- C3: `assets.pde` mantém fallback geométrico para ícones e piso sem arte.
- C4: `hud.pde` conserva mapeamento explícito de energia, oxigênio, água, comida, peças e moral, incluindo valor, barra, cor, alerta crítico e ordem.
- C5: `capture.pde` registra construções, invalidações e memória adicional no CSV ou resumo final; não há tabela ou endpoint associado.

**US-02 — Comparar baseline e versão revisada em condições equivalentes**

- C1: `--metrics` é o cenário de performance; `--capture`, `--hit-test`, `--ladder-test` e `--asset-pipeline-test` seguem a regressão funcional. Cada captura produz sidecar com `environment`, `machine`, `assets`, `room`, `state`, `nominal_window_s` e `processing`.
- C2: `compare-metrics.mjs` exige três amostras e `nominal_window_s` igual a trinta; o CSV separa `duration_real_s` das métricas numéricas.
- C3: `compare-metrics.mjs` registra antes, depois e variação para mediana e p95 de tempo de quadro; carregamento, memória, construções e invalidações ficam por amostra ou em resumo.
- C4: a conclusão exige alguma redução mensurável e reproduzível, sem percentual mínimo arbitrário.
- C5: medição não confiável ou ausência de redução gera status inconclusivo.
- C6: a mediana dos três p95 de cada métrica agregável é comparada; variação superior a 10% mantém a falha existente.

**US-03 — Remover somente código comprovadamente não utilizado**

- C1: cada remoção exige busca de referências estáticas no repositório.
- C2: a análise cobre entrypoints Processing, nomes globais entre abas, entradas de teclado e mouse, modos do harness e scripts chamados pelo `package.json`.
- C3: código alcançado por harness, modo de teste, compilação implícita ou entrada documentada não é classificado como morto.
- C4: a validação correspondente é executada depois de cada remoção ou consolidação relevante.
- C5: nenhum cenário de equivalência é removido, enfraquecido ou alterado para ocultar regressão.
- C6: `code/VERIFICATION.md` registra, para cada remoção, arquivo e símbolo, buscas de referências, entrypoints e entradas indiretas examinados, justificativa da classificação, validação posterior e resultado.

**US-04 — Consolidar lógica duplicada em helpers explícitos**

- C1: texto com sombra, rodapé, arte de NPC, preparação de portal, mapeamento de recursos e preparação de imagens ficam com um único contrato compartilhado quando aplicável.
- C2: a consolidação preserva textos, posições, cores, tamanhos, fallback, orientação dos sprites, halos, som, chegada, retorno e ausência de asset.
- C3: o helper de geometria de botão usa a mesma área para desenho, cursor, teclado e hit-test.
- C4: helpers não decidem regras de gameplay de quest, incidente ou modal.
- C5: todas as referências dependentes de nomes, localizações ou assinaturas alteradas são atualizadas antes da regressão.
- C6: antes da primeira edição, um inventário lista cada duplicação candidata por arquivo, símbolo, categoria, referências e decisão; somente itens desse inventário podem ser consolidados, e itens semelhantes mantidos devem registrar a justificativa.

**US-05 — Remover comentários dos arquivos executáveis**

- C1: comentários de código e blocos de comentário dos `.pde`, `.mjs` e `.sh` cobertos são removidos.
- C2: shebangs e diretivas obrigatórias permanecem no local correto.
- C3: documentação em `docs/`, `code/`, `mechanics/`, `events/`, `interface/` e demais áreas documentais não é alterada por essa limpeza.
- C4: módulos `.mjs` passam por `node --check` e scripts Bash mantêm diretivas de execução válidas.
- C5: strings exibidas, dados editoriais, expressões Processing e comandos operacionais não mudam.
- C6: a auditoria enumera cada arquivo coberto por extensão e caminho, confirma comentários removidos e registra exceções preservadas.
- C7: o escopo autoritativo é a lista de arquivos rastreados pelo repositório com extensões `.pde`, `.mjs` e `.sh`, incluindo `last_horizon/editorial.pde` e os scripts operacionais de `tools/`; somente saídas geradas e diretórios transitórios ficam excluídos.
- C8: comentários `//`, `/* ... */` e `#` lexicais, inclusive JSDoc e comentários após código, são removidos; shebangs e diretivas necessárias permanecem, e sequências dentro de strings não são tratadas como comentários.
- C9: a auditoria em `code/VERIFICATION.md` registra caminho, extensão, contagem antes/depois e cada exceção preservada, além do comando e do código de saída usados para verificá-la.

**US-06 — Separar blocos coesos em abas procedurais**

- C1: cenário e nave, portais, movimento, animação e áudio permanecem identificáveis por suas abas.
- C2: a movimentação de código é mínima e rastreável, preservando expressões, ordem de atualização, inicialização e chamadas de áudio.
- C3: o sketch compila como unidade com e sem os módulos opcionais previstos.
- C4: globais, funções entre abas e dependências de inicialização continuam disponíveis no momento de uso.
- C5: a validação final confirma campanhas, física, animação, áudio, escadas e travessias de porta.
- C6: o inventário autoritativo inclui `editorial.pde`, e a entrega não adiciona nenhuma nova aba `.pde`.

**US-07 — Preparar transição entre salas uma única vez**

- C1: `preparePortalTransition()` resolve destino, saída, chegada, direção e retorno antes de escolher caminho animado ou imediato.
- C2: a saída é capturada antes da movimentação e o retorno reaproveita a posição quando essa é a regra atual.
- C3: coordenadas arbitrárias, ida, volta, gravidade e travessias entre conveses mantêm o resultado.
- C4: arte completa mantém fases e som; arte ausente não bloqueia a partida.
- C5: o estado preparado é limpo na entrada ou encerramento e não vaza para outra porta.
- C6: uma nova entrada durante a abertura, execução ou fechamento é ignorada. Porta inválida, destino inexistente, retorno ausente ou preparação inválida limpa o estado preparado, mantém o jogador na sala atual e usa fallback visual e sonoro; falha de áudio não interrompe a transição, e o diagnóstico registra a causa.

**US-08 — Preservar quests e ciclo diário**

- C1: ofertas preventivas, incidentes, soluções, seleção, confirmação presencial, coleta, entrega, retomada e socorro mantêm estados e pontos físicos.
- C2: o técnico carrega no máximo um objeto por vez e cada conclusão consome o limite diário.
- C3: custos, recompensas, perdas, prazos, negligência, riscos, crises, mortes, vitória e derrota permanecem iguais aos valores de referência.
- C4: quatro cômodos, quatro sobreviventes além do técnico, seis recursos e dez dias continuam presentes.
- C5: validação cobre os caminhos de quest e rejeita qualquer alteração de resultado observável mesmo com compilação bem-sucedida.

As condições fatais são registradas na ordem energia, oxigênio, moral, motor e sobreviventes; derrota prevalece sobre vitória quando ambas seriam possíveis no último dia.

- C2: `processNight()` parte do mesmo contrato, aplica uma projeção e não repete perdas ou consequências.
- C3: a previsão contém consumo, perdas, falhas, riscos, prazos, crises, condições fatais e desfecho aplicável.
- C4: estados equivalentes produzem os mesmos valores e resultado em previsão e noite processada.
- C5: snapshots, fixtures e restaurações não deixam estado residual.
- C6: a prévia guarda a `NightProjection` exibida e uma cópia/assinatura do estado de origem. A confirmação aplica esse mesmo objeto uma única vez; qualquer mudança no estado de origem invalida a prévia, bloqueia a confirmação obsoleta e exige uma nova projeção, sem recalcular duplicadamente durante a confirmação.

**US-10 — Unificar decisão do modal ativo**

- C1: prioridade entre pausa, transmissão, incidente, ordens, mapa, diálogo, painel técnico, sono, ajuda e cena é preservada.
- C2: fechamento de transmissão, `ESC` no detalhe e `ESC` na comparação seguem os retornos e preservações definidos.
- C3: fechar painel não cancela ordem aceita; estados pendentes são limpos apenas no caminho correto.
- C4: controles encobertos nunca recebem clique ou confirmação.
- C5: hit-test, cursor, mouse, `ENTER` e `ESC` seguem a camada desenhada.

**US-11 — Manter harness e modo de teste desacoplados**

- C1: o runtime compila e executa com hooks opcionais inertes quando `capture.pde` e `test_mode.pde` estão ausentes.
- C2: o harness mantém `--capture`, `--hit-test`, `--ladder-test`, `--asset-pipeline-test` e `--metrics`.
- C3: Ctrl+K, teleporte e destaque visual continuam no modo manual quando incluído no ambiente de desenvolvimento.
- C4: destaque forçado não autoriza pagamento, aceite, entrega ou conclusão indevida.
- C5: a matriz de combinações com módulos opcionais confirma todas as compilações previstas.

A matriz obrigatória de compilação é:

| Combinação | `capture.pde` | `test_mode.pde` | Resultado esperado |
|---|---:|---:|---|
| Base | ausente | ausente | runtime compila e executa sem hooks |
| Captura | presente | ausente | runtime compila e disponibiliza os modos do harness |
| Manual | ausente | presente | runtime compila e disponibiliza Ctrl+K, teleporte e destaque |
| Completa | presente | presente | runtime compila com harness e modo manual simultaneamente |

Uma falha em qualquer combinação é `FAIL`; combinação não executada por ausência de Processing ou pré-requisito é `INCONCLUSIVO` e não conta como evidência.

- Contrato preservado: `snapshot-entrega.mjs` herda sua lista vigente de exclusões para harness, modo manual, ferramentas de verificação, protótipo de balanceamento e artefatos transitórios. O script gera `output/snapshot-entrega-manifest.json` com os caminhos excluídos e os arquivos de runtime mantidos; a cópia final deve compilar, e o manifesto deve comprovar que não expõe Ctrl+K, teleporte, destaque forçado ou overlay de modo de teste.

**US-12 — Produzir registro único de equivalência, custo e limitações**

`code/VERIFICATION.md` deve seguir esta estrutura fixa:

```markdown
# Registro de verificação
## Identificação
- baseline: referência, commit/hash e manifesto
- versão revisada: referência, commit/hash e manifesto
- perfil e ambiente: hardware, GPU, OS e Processing
## Comandos e pré-requisitos
| verificação | comando | pré-requisito | timeout | status | evidência | limitação/impacto |
## Equivalência funcional
| cenário/fixture | baseline | versão revisada | status | diferença |
## Métricas de custo
| custo | baseline | versão revisada | variação | status |
## Limitações e cenários não executados
| item | motivo | impacto | status |
## Decisão
- status geral: PASS, FAIL ou INCONCLUSIVO
- justificativa e próximo passo
```

Os únicos status normativos são `PASS`, `FAIL` e `INCONCLUSIVO`. “Não executado” é uma condição descrita na coluna de limitação e recebe `INCONCLUSIVO`; comando iniciado que falha, viola contrato ou excede timeout recebe `FAIL`. Hashes, versões e caminhos dos artefatos devem identificar exatamente as referências comparadas.

- C1: `code/VERIFICATION.md` identifica baseline, versão revisada, comandos, cenários, métricas, variação e estado das verificações.
- C2: diferenças, limites, métricas indisponíveis e cenários não executados ficam explícitos.
- C3: limitação de ambiente nunca é apresentada como ganho ou prova de equivalência.
- C4: o registro combina métricas com regressão funcional existente.
- C5: a entrega só é pronta quando verificações disponíveis passam, limitações estão documentadas e há redução mensurável e reproduzível; sem isso, otimização fica inconclusiva.

#### Métricas de sucesso

- Redução de custo comprovada: pelo menos um custo alvo entre preparação inicial, render por quadro, carregamento de assets ou construção de cache apresenta redução mensurável e reproduzível na comparação baseline versus versão revisada, com três amostras e janela nominal de trinta segundos.
- Ausência de regressão de performance: para cada métrica agregável com p95, a mediana dos três p95 da versão revisada não varia mais de 10% em relação à baseline; variações acima desse limite são falhas do comparador.
- Otimização robusta: baseline e versão final são medidas no notebook Core i3 com vídeo integrado do usuário e no perfil de referência; o p95 agregado de tempo de quadro é no máximo 33,3 ms, os demais custos E6 não regridem mais de 10%, não há crescimento persistente de alocações por quadro e não há falha de carregamento.
- Preservação funcional: `--capture`, `--hit-test`, `--ladder-test` e `--asset-pipeline-test` passam pela regressão existente, cobrindo ciclo, quests, noite, riscos, menus, hit-test, escadas e carregamento de PNG.
- Equivalência noturna: estados equivalentes produzem os mesmos valores e resultados entre `projectNight()` e `processNight()`, sem efeitos repetidos nem estado residual.
- Compilação: o sketch compila e executa como unidade com os módulos opcionais e sem `capture.pde` e `test_mode.pde`.
- Limpeza auditada: a auditoria enumera `.pde`, `.mjs` e `.sh`, confirma remoção de comentários de código e registra shebangs e diretivas obrigatórias preservados.
- Registro verificável: o registro final reúne comandos, cenários, métricas, variações, resultados e limitações; cenários não executados ou métricas sem amostra ficam explícitos e não contam como evidência.

#### Dependências e riscos

Dependências preservadas:

- O runtime depende do contrato compartilhado entre abas Processing, da ordem necessária de inicialização e das variáveis e funções globais entre arquivos.
- `tasks.pde`, `game.pde` e `night_projection.pde` dependem dos estados de quests, calendário, snapshots e projeções noturnas.
- `hud.pde`, `ui.pde`, `screens.pde`, `ship.pde` e `portals.pde` dependem dos contratos de renderização, camadas modais, hit-test, navegação e fallbacks de assets.
- O harness e `tools/` dependem de fixtures, entrypoints, modos de teste, comandos do `package.json` e caminhos documentados.
- `mechanics/ACTIONS.md`, `events/`, `interface/ROOMS.md`, `docs/CURRENT_IMPLEMENTATION.md`, `docs/adr/` e `code/VERIFICATION.md` orientam a validação dos contratos existentes.
- A medição depende de Processing 4.5.6, assets, máquina, sala, estado, janela nominal e demais campos equivalentes no manifesto.

Riscos e controles:

- Dependências implícitas entre abas: manter compilação como unidade e validar após cada consolidação relevante.
- Remoção indevida de código alcançado indiretamente: combinar busca estática, entrypoints, entradas, modos de teste e regressão posterior.
- Divergência no ciclo noturno: manter `simulateNightTransition()` sem efeitos colaterais, comparar estados equivalentes e verificar ausência de resíduo.
- Quebra da prioridade de modais: usar uma única resolução de camada e validar desenho, teclado, cursor e hit-test.
- Medição inconclusiva ou não comparável: registrar manifestos, variação e limitações; manter a otimização inconclusiva.
- Custo de memória dos caches: registrar memória adicional e limitar caches a representações estáticas, sem números, barras, cores de estado ou piscadas do HUD.
- Remoção de comentários que afete execução: preservar shebangs, diretivas, strings e expressões; executar `node --check` e validações Bash.
- Enfraquecimento do harness: preservar fixtures e cenários de equivalência; não remover testes para reduzir contagem de linhas.

## 5. Security

### 5.1 Auth Flow Completo

Não existe fluxo de autenticação porque o produto é uma aplicação local e offline sem usuários remotos, servidor, banco, sessão ou token.

O fluxo operacional de segurança e empacotamento é:

1. O runtime local é executado com as abas Processing existentes e estado global em memória.
2. O modo de desenvolvimento pode incluir `test_mode.pde`, permitindo Ctrl+K, teleporte e destaque visual para validação manual.
3. O destaque visual forçado não autoriza pagamento, aceite, entrega ou conclusão de quest.
4. O harness pode ser incluído para capturas, hit-test, ladder test, pipeline de assets e métricas.
5. `snapshot-entrega.mjs` remove harness, modo manual, ferramentas de verificação, protótipo de balanceamento e artefatos transitórios conforme a lista de exclusões vigente.
6. O snapshot final não expõe Ctrl+K, teleporte, destaque visual forçado, overlay de modo de teste ou controles exclusivos de desenvolvimento.

Não há register, login, logout, session expired, refresh token, cookie, header de autorização ou protected route a implementar.

### 5.2 Checklist de Seguranca

- [x] Session config (cookie flags, expiração): não aplicável; não há sessão, cookie ou usuário remoto.
- [x] RLS ativo em todas as tabelas: não aplicável; não há banco nem tabela.
- [x] CORS configurado: não aplicável; não há servidor HTTP.
- [x] Rate limiting ativo: não aplicável; não há serviço exposto.
- [x] Input validation em todos os endpoints: não há endpoints; entradas de CLI e manifestos são validadas pelos scripts existentes, especialmente `compare-metrics.mjs`.
- [x] Webhook signature verification: não aplicável; não há webhook ou integração externa.
- [x] Secrets em env vars (nunca hardcoded): não há secrets nem variáveis de ambiente de produto definidas pelo PRD.
- [x] File upload validation (tipos, tamanho): não aplicável; não há upload. O pipeline local de PNG deve manter o teste de carregamento e fallback existentes.
- [x] Snapshot sem controles de desenvolvimento: exclusões vigentes de `snapshot-entrega.mjs` devem continuar removendo os módulos e artefatos de desenvolvimento.
- [x] Integridade do harness: fixtures e cenários não podem ser removidos ou enfraquecidos para fazer a regressão passar.
- [x] Integridade de scripts: `.mjs` passa por `node --check`; `.sh` mantém shebang e diretivas obrigatórias.

### 5.3 .env.example

Não há variáveis de ambiente necessárias para esta aplicação. O arquivo `.env.example` deve ser inexistente ou vazio conforme a convenção já adotada pelo repositório; não devem ser inventadas variáveis para Processing, autenticação, banco, CORS, rate limiting ou APIs externas.

O ambiente de execução deve disponibilizar localmente Processing 4.5.6, Node.js e Bash quando os cenários correspondentes forem executados. Essa dependência é documentada como pré-requisito operacional, não como variável de ambiente de produto.
